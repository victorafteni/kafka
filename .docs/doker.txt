ce face zookeper?

ZooKeeper acts as the central coordinator for distributed systems like Kafka, essentially functioning as the cluster's brain or orchestrator. Its core responsibilities include maintaining broker metadata, tracking which brokers are actively online, and managing cluster membership information.

Apache ZooKeeper este un serviciu centralizat de coordonare și consens pentru sisteme distribuite.

Dacă privim Kafka ca pe o flotă de camioane de mare viteză care transportă mesaje (date), ZooKeeper este „turnul de control” (dispeceratul) care știe în permanență starea fiecărui nod din cluster.

Principalele roluri ale lui ZooKeeper în Kafka

Gestiunea brokerilor și detectarea căderilor (Cluster Membership):

Fiecare broker Kafka (commerce-kafka) se înregistrează la pornire în ZooKeeper printr-o sesiune cu „bătăi de inimă” (heartbeats).
Dacă un nod Kafka cade sau are probleme de rețea, ZooKeeper detectează pierderea conexiunii și notifică restul clusterului pentru a redistribui traficul.

Alegerea liderului clusterului (Controller Election):

Dintre toți brokerii Kafka existenți, unul singur trebuie să fie Controller-ul (nodul care decide cine e responsabil de ce partiție).
ZooKeeper este cel care organizează alegerile democratice: dacă liderul actual cade, ZooKeeper alege imediat un nou broker ca lider.

Gestiunea metadatelor pentru Topice și Partiții:

Când creezi un topic (ex. page_views cu 3 partiții):
Unde se află fizic partiția 0, 1 sau 2?
Cine este Partition Leader (nodul care scrie/citește) și cine sunt Followers (replicile de rezervă)?
Toate aceste metadate critice sunt sincronizate și stocate în arborele de noduri ZooKeeper (znodes).

Configurații și permisiuni (ACLs & Quotas):

Regulile de securitate, listele de acces (cine are voie să scrie/citească dintr-un topic) și cotele de bandă pe client sunt sincronizate prin ZooKeeper.
O analogie practică
Fără ZooKeeper	Cu ZooKeeper
Nodurile Kafka nu ar ști dacă celelalte noduri sunt în viață.	Se știe în sub-secundă starea fiecărui broker.
În caz de pană pe un server, clienții nu ar ști la ce server să trimită mesajele.	ZooKeeper redirecționează clienții către noii lideri de partiție.
Ar apărea riscul de split-brain (două noduri cred ambele că sunt liderul).	ZooKeeper garantează un singur lider la un moment dat (Consensus).
💡 Context modern: Kafka KRaft (Fără ZooKeeper)

În versiunile mai recente de Apache Kafka (3.0+), a fost introdus protocolul KRaft (Kafka Raft), prin care Kafka își gestionează propriul consens intern fără a mai avea nevoie de ZooKeeper. Totuși, în majoritatea companiilor mari și a imaginilor enterprise Confluent (cum este cea din docker-compose.yml), ZooKeeper este încă utilizat pe scară largă pentru stabilitate.

# Extindere arhitectură existentă — Angular + Node.js/Express + Redis + Kafka + Docker

## 1. Contextul actual al proiectului

Am un mini-proiect de shop online.

În acest moment arhitectura EXISTĂ deja și funcționează astfel:

```text
Angular
   │
   │ HTTP
   ▼
Node.js + Express
   │
   └── servește deja:
       ├── Categories
       └── Products
```

Node.js + Express este deja implementat și este backend-ul actual al aplicației.

**NU crea un backend Node.js/Express nou.**

**NU duplica API-ul existent.**

Trebuie să extinzi backend-ul Node.js + Express existent pentru a introduce:

1. Redis pentru stocarea/cache-ul produselor și categoriilor;
2. Kafka pentru event tracking;
3. Docker pentru Redis și Kafka;
4. page tracking din Angular prin API-ul Express existent.

---

Vreau ca arhitectura să devină:

```text
                         ┌─────────────────┐

                       │ Products API       │
                       │ Categories API     │
                       │ Redis Service      │
                       │ Kafka Service      │
                       │ Tracking API       │
                       └─────────┬─────┬────┘

                                 │     ▼
```

```text
      save products in Redis
      return products
```

Pentru:

```http

```

același mecanism.

```json
  "session_id": "...",
  "anonymous_id": "...",
  "user_id": null,
  "payload": {
    "path": "/products",
    "route": "products",
    "title": "Products",
    "referrer": "/"
  }
}
```

Această structură trebuie să permită ulterior:
